Work/PlayAlong

Case study 01 · Desktop application · Applied ML

Take out the part you want to practice.

If you play bass or piano, like myself, practising with a recording puts you in a strange position. You are playing along with someone who is already playing your part, slightly differently, slightly ahead of you. You cannot hear your own mistakes, because the recording covers them. PlayAlong is a Windows app that removes just the bass or just the piano from a song you own, leaves everything else exactly as it was, and never sends your audio anywhere.

01The problem

Karaoke solved this for singers forty years ago. Instrumentalists are still waiting.

Plenty of people have taken a run at this and several of them landed it — Moises, LALAL.AI and Spleeter will all pull a song into separate stems, and the good ones do it well. PlayAlong is deliberately narrower. It removes exactly one of two instruments, bass or piano, because those are the two I play, and that single constraint turns an open research problem into one I can actually finish and defend. It also rules out every workaround a musician normally reaches for: official backing tracks exist for maybe a few hundred songs; isolating a stem hands you your own part on its own with no band behind it; and EQ tricks that scoop out the low end take the kick drum with them. What is left is three requirements. It has to be the song you actually chose — not an approximation, not a MIDI re-creation, but your own MP3 or WAV handed back minus one instrument. Everything you did not ask to remove has to survive intact: drums, vocals, guitars, synths and room ambience, with no quietly dulled kick and no smeared reverb tail. And none of it can leave the machine, because uploading someone's music library is a privacy problem and a licensing problem that I would then own. Every decision on the rest of this page follows from those three.

03The decision that mattered

Subtract the instrument. Do not rebuild the song.

Every separation model returns a set of estimated stems. The obvious move is to add the ones you want back together. PlayAlong deliberately does not do that — and the reason is the strongest engineering argument on this page.

Why this is better than summing stems

A six-stem model splits a song into six estimates. Add five of them back together and you inherit five sets of errors: every artefact, every smeared transient, every bit of reverb the model assigned to the wrong bucket.

Subtracting uses the model exactly once. Anything it failed to identify as bass stays in the output bit-for-bit identical to the original file. The drums are not "reconstructed drums" — they are the drums.

The failure mode also gets much friendlier. A weak estimate leaves a little bass audible, which is harmless. Summed stems fail by making the whole track sound underwater.

04Architecture

Five steps, each one replaceable.

Click through the pipeline. The code shown is the real implementation, not pseudocode.

Normalise the input before the model sees it

MP3 and WAV arrive at any sample rate, channel count, or bit depth. FFmpeg converts everything to the one format the model expects, in 32-bit float so no quantisation happens on the way in. FFmpeg ships with the app via imageio-ffmpeg — users never install it. 

command = [
    str(ffmpeg_path), "-hide_banner", "-loglevel", "error", "-y",
    "-i", str(input_path),
    "-vn",                  # drop cover art / video streams
    "-ac", "2",             # force stereo
    "-ar", "44100",         # the rate the model was trained on
    "-c:a", "pcm_f32le",    # float — nothing is rounded off
    str(output_path),
]
src/playalong/audio_tools.py

Two modes, two different models

Bass uses the fine-tuned four-stem model, which is stronger at bass than anything else available. Piano needs the six-stem model, because it is the only one with a piano output at all. The mapping is a plain lookup table, so swapping in a better piano model later is a one-line change with no effect on the UI or the audio code. 

MODEL_BY_MODE = {

Run the model, then verify its contract

The separator returns a dictionary of stems. Rather than trusting that the requested key exists, the engine checks and fails with a message that names what the model did return. A model swap that silently produces the wrong stem set becomes an obvious error instead of a confusing crash. 

separator = self._separator_factory(
    model=model.name, shifts=1, split=True,
    overlap=0.25, progress=False,
)
mixture, separated = separator.separate_audio_file(str(decoded_mix))

target_key = model.target_stem.lower()
if target_key not in separated:
    available = ", ".join(sorted(separated))
    raise RuntimeError(
        f"Model {model.name} did not return {target_key}. "
        f"Available: {available}"
    )
src/playalong/engine.py

One subtraction, 24-bit out

The estimated stem is subtracted from the original mixture. Output is 24-bit rather than 16-bit specifically because subtraction can push peaks past full scale; the extra headroom means the fix is a gentle global scale rather than clipping. Nothing is re-encoded to a lossy format. 

save_audio(
    mixture - target,
    temporary_output,
    samplerate=samplerate,
    bits_per_sample=24,
)
src/playalong/engine.py

Never destroy a file the user already had

Two safeguards. The result is written to a hidden partial file and only renamed into place once it is complete, so a crash mid-render cannot leave a corrupt WAV with a valid-looking name — Path.replace() is atomic on the same volume. Separately, an existing output is never overwritten; the app picks the next free number instead. 

temporary_output = output_path.with_name(f".{output_path.name}.partial.wav")
save_audio(mixture - target, temporary_output, ...)
temporary_output.replace(output_path)     # atomic rename


def _unique_path(preferred: Path) -> Path:
    if not preferred.exists():
        return preferred
    for number in range(2, 10_000):
        candidate = preferred.with_name(
            f"{preferred.stem}_{number}{preferred.suffix}"
        )
        if not candidate.exists():
            return candidate

05Engineering decisions

Six choices, and what each one bought.

Anyone can list a stack. These are the trade-offs I would defend in a review.

Testability

Every external dependency is injected

The engine takes the separator, FFmpeg locator, decoder and writer as constructor arguments. The production defaults load PyTorch and a 2 GB model. The tests pass in a fake that returns the string "mixture", so the whole suite runs in milliseconds on a laptop with no model weights and no GPU. That single choice is the reason this project has meaningful tests at all.

Responsiveness

Separation runs on a QThread, never the UI thread

A worker object is moved onto a real thread and reports progress through Qt signals. Separation takes minutes. Doing it inline would give Windows a frozen, "not responding" window — users would assume it crashed and kill it. Status text, an indeterminate progress bar, and disabled controls make a long wait legible instead of alarming.

Privacy

Local-only processing, telemetry off

Model weights cache to %LOCALAPPDATA% on first use; after that the app never touches the network. TORCH_HOME and HF_HOME are redirected so downloads land in the app's own folder rather than scattered across the user profile, and Hugging Face telemetry is explicitly disabled. Nobody's music library gets uploaded to a server I would then have to secure.

Distribution

FFmpeg ships with the app; weights do not

A bundled FFmpeg wheel is copied into the runtime folder, but only if the system does not already have one on PATH. "Install FFmpeg and add it to your PATH" is where most audio tools lose non-technical users. Model weights stay outside the executable and download on demand, which keeps the installer to a sane size and lets a model be replaced without shipping a new build.

Correctness

Validation lives in the domain layer, not the UI

A frozen SeparationRequest dataclass validates itself; the window simply shows whatever it raises. Unsupported extension, missing file, output path that is not a folder — all rejected in one place with messages written for a musician rather than a developer. The UI cannot construct an invalid job even if I later add a command-line entry point.

Maintainability

The model is behind an interface, not scattered through the app

Everything Demucs-specific sits behind DemucsEngine and a small SeparatorLike protocol. Piano separation is the weakest part of the current model landscape. When a better piano model appears — and it will — it slots in without touching the interface, the threading, or the file-writing logic. The architecture assumes it will be replaced.

  • 01

    Model routing is verified, not assumed

    A parametrised test asserts that Bass mode loads htdemucs_ft and Piano mode loads htdemucs_6s. Wiring the wrong model to a mode is the kind of bug that is invisible by ear until you A/B it.

  • 02

    Data loss is the test I care about most

    One test plants a file at the output path, runs a job, and asserts the original bytes are untouched and the result landed at _2. Users point this app at their own music folder.

  • 03

    The real boundaries still get exercised

    A separate suite runs actual FFmpeg against a generated WAV and writes a real tensor to disk, so the fakes cannot drift away from the interfaces they stand in for.

  • 04

    Linting is part of the definition of done

    Ruff runs with rules for bugbear, simplification, import order and modern syntax — a 100-character line limit and no unused-argument shortcuts.

08Limitations

What it does not do yet.

Every one of these is a known trade-off rather than an oversight.

  • 01

    Piano separation is the weak link

    The six-stem model's piano output is noticeably less clean than its bass output, especially against overdriven guitar. It is usable for practice; it is not transparent. This is a model limitation, which is exactly why the model sits behind an interface.

  • 02

    Processing is slow on CPU

    Minutes per song without a GPU. There is no progress percentage because the underlying call does not expose one — an indeterminate bar that tells the truth beat a fake percentage that lies.

  • 03

    Windows only, MP3 and WAV only

    Scope was cut deliberately to get a working tool rather than a broad, half-finished one. The path handling already uses a cross-platform fallback, so a macOS build is mostly a packaging exercise.

Where it goes next

A batch queue so a full practice set can be prepared in one pass overnight, and a preview player so users can hear the result before committing a file to disk.

Longer term, the more interesting problem is evaluation: I want a proper listening test against a licensed multitrack set, so "the new piano model is better" becomes a number rather than an opinion.

The application code is MIT licensed. Separation is powered by the MIT-licensed Demucs project; any commercial build would need a full audit of the licence terms attached to every shipped model weight.

09How this was built

The scoping did more work than the model did.

PlayAlong was built with an AI coding agent across two sessions. I set the problem, made the product calls, and rejected the versions that were wrong; the agent wrote the implementation and ran the verification. Every decision below is quoted from the session log, which is linked at the end.

Five minutes 5:51 → 5:56 17 July 2026
what if we combined vocals and drums into other? I only want to be able to practice along while playing either the bass or the piano

Five minutes earlier I had asked how close we could get to Moises — a five-stem separator, months of work, an evaluation problem I had no dataset for. That one message deleted most of the project. It reframed "separate this song into five parts" into "remove one part," which is a strictly easier problem with a strictly better result: the stems I never asked for never get degraded.

    Made the stack justify itself. Python won on merit — the separation models and GPU support live in PyTorch — but it had to be argued for rather than assumed. The same pass pinned Python 3.13 instead of the machine's 3.14, because PyTorch releases lag new runtimes.

    can we not make it export the file in the new key? it should be able to change the pitch and play the audio back within the app without saving another file.

    A workflow correction on the companion app. KeyShift had been built as an exporter, which is wrong for practice — nobody wants a folder of near-duplicate WAVs to audition one key. It was rebuilt to process in memory and play back in-app. The delivered version was working software; it was still the wrong product, and that is a judgement call no test suite catches.

What I decided

  • The problem worth solving, and the four-fifths of it worth deleting
  • Two practice modes, one output file, no feature beyond that
  • That the stack had to be argued for, not defaulted to
  • That KeyShift's export workflow was wrong and had to be rebuilt
  • That processing stays local, because uploading someone's music library is a problem I would then own

What the agent did

  • Wrote the implementation, the tests, and the packaging scripts
  • Surveyed current separation research and recommended HTDemucs variants per mode
  • Proposed mixture − target once the problem had been narrowed to one instrument
  • Ran the verification: seven tests, linting, live model loads, real FFmpeg decoding
  • Diagnosed the dependency and packaging failures listed below

10What broke

Five failures worth writing down.

None of these are in the source, so they are invisible to anyone reading the repository. They are most of where the time actually went.

Dependency

A broken transitive dependency forced a backend change

The first backend, audio-separator, pulled a diffq source archive that does not build on Windows under Python 3.14. The fix was not a patch but a replacement: Demucs 4.1 had made that quantisation dependency optional and exposed an official Python API. Switching removed the broken dependency entirely and handed back the mixture and target tensors directly — which is what made the subtraction approach clean to implement.

Tooling

The installer reported success after pip had failed

A setup script that lies is worse than one that crashes. The script was not checking pip's exit status, so a failed install printed a success message and the first error a user would have seen would have been an import failure much later, with no obvious cause. Exit-code handling was fixed before anything else was allowed to proceed.

Upstream bug

Demucs 4.1 omits NumPy from its declared dependencies

The published wheel does not list NumPy even though its transformer code imports it, so a clean install produced an app that only failed once a model actually ran. A smoke test that exercised real inference caught it; unit tests with mocks never would have. NumPy is now an explicit dependency of this project so users do not inherit the upstream packaging bug.

Privacy

Model weights were landing in the shared Hugging Face cache

First-run downloads defaulted to the machine-wide cache, scattering gigabytes outside the app and entangling PlayAlong with any other tool using the same directory. Redirecting TORCH_HOME and HF_HOME keeps everything under the app's own folder — predictable to find, and trivial to delete when someone uninstalls.

Environment

PowerShell execution policy blocked the launcher

The setup and run scripts could not execute on the target machine at all. The wrong fix is telling the user to weaken their system's security policy. Instead the app ships .bat launchers that invoke the verified PowerShell scripts with a process-scoped bypass, so double-clicking works and the computer's policy is left exactly as it was.
