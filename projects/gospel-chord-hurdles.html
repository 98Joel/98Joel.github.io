Work/Gospel Chord Hurdles

Case study 02 · Desktop game · Real-time audio

You cannot jump the hurdle until you play the chord.

A runner is heading for a wall with a chord symbol painted on it. There is no jump button — the only control is a piano. Play the right notes in time and the wall opens. Miss it, and the game does not end your run. It backs up, shows you the notes you needed, and waits until you say you are ready.

01The problem

Every musician knows the chord chart. Almost nobody can play it in time.

Gospel piano runs on a vocabulary that is written down everywhere and practised almost nowhere: 6/9 chords, thirteen-sus, rootless dominants, passing diminished. You can read what notes are in an A♭13sus in about four seconds. Getting your hands to find it, in tempo, without looking, takes months.

The gap is not knowledge. It is recall under time pressure — and that is a drilling problem, which is the one thing games are genuinely good at. So the chord chart became a lane of hurdles, and the only way through is to play.

  • 01

    The instrument has to be the controller

    Not arrow keys with a chord displayed next to them. If you can clear a hurdle without your hands being in the right shape, the game has taught you nothing.

  • 02

    It has to accept how a real player voices a chord

    Nobody plays a textbook root-position triad. The same chord gets played inverted, spread across two hands, with the root in the bass or missing entirely. All of that has to count as correct.

  • 03

    Failing has to be worth something

    The moment you get a chord wrong is the moment you most need to be told what it was. A game-over screen throws that moment away.

  • 04

    Silence makes it a spelling test

    Chord after chord with nothing behind it is a flashcard drill with extra steps. Practising musically means practising against a band.

03The decision that mattered

Missing a chord is not a loss condition. It is the lesson.

The first version was an arcade game: hurdles came faster, you eventually failed, you started again. It worked. It was also useless, and one message from the person who had to practise on it deleted the entire premise.

One message Four decisions 1 July 2026
ok so this game is supposed to be more of learning than challenging/testing

That clause reclassified the project. A game that tests you optimises for difficulty curves and failure states. A game that teaches you optimises for the moment you get it wrong — which meant the failure state, the difficulty ramp, and the launch behaviour were all now wrong, and the same message said so.

What the rest of that message changed

"the cords should be in different sections" — difficulty stopped being a timer. There are now six sections — from plain triads up to rootless dominants and quartal stacks — plus an all-voicings mode for when you want the old behaviour, and you pick. The game no longer decides you are ready for thirteen-sus because you survived ninety seconds.

"the game should rewind a little bit, tell me the chord tones, ask me if I'm ready" — a third application state. Not playing, not stopped: paused mid-lane with the answer on screen and the same hurdle still standing there.

"the game shouldn't start immediately I launch the file, that's weird" — a menu. Small change, and the one that most affects whether a first-time player feels ambushed. 

// Three states, because "paused" and "stopped"
// are not the same thing to a learner.
enum class PracticeState
{
    Menu,
    Playing,
    TeachingPause
};

// The hurdle you missed is not destroyed.
// It backs up and waits for you.
void rewindForChord (size_t hurdleIndex)
{
    auto hurdle = hurdles[hurdleIndex];

    hurdle.x      = runnerX() + 170.0f;
    hurdle.judged = false;

    hurdles.clear();
    hurdles.push_back (hurdle);

    teachingChordIndex = hurdle.chordIndex;
    practiceState      = PracticeState::TeachingPause;
    accompaniment.setRunning (false);
}

  • 01

    There is no score penalty for missing

    The counter is labelled Reviews, not Mistakes. Points are only ever added. The only thing a miss costs you is your streak bonus and the seconds you spend reading the answer — which is the part you actually wanted.

  • 02

    The band stops when the teaching card appears

    One line: accompaniment.setRunning(false). A drum loop under an explanation is noise, and the silence is what makes the pause read as "read this" rather than "you lost".

  • 03

    You get the same chord back, not a new one

    The missed hurdle is the only one left on screen. The lane is cleared and it is re-placed just ahead of the runner, so the first thing you do after being told the answer is play it.

04How it recognises a chord

Five steps between your fingers and the verdict.

Click through. The code shown is the real implementation, lightly trimmed for width.

Three input devices, one source of truth

A note can arrive from a USB piano, from clicking the on-screen keyboard, or from the computer keyboard's piano layout. Rather than handle three cases, all three are funnelled into JUCE's MidiKeyboardState, and the game listens to that one object. Adding a fourth input later costs nothing. 

// A plain 128-slot table: is this MIDI note down right now?
std::array<bool, 128> activeNotes {};

void handleNoteOn (juce::MidiKeyboardState*, int, int midiNoteNumber, float) override
{
    const juce::ScopedLock lock (activeNoteLock);

    if (juce::isPositiveAndBelow (midiNoteNumber, (int) activeNotes.size()))
        activeNotes[(size_t) midiNoteNumber] = true;
}
Source/Main.cpp

128 keys collapse into 12 names

This one line is why the game feels fair. A piano has 128 MIDI notes, but music only has twelve note names — every C is a C. Taking the remainder after dividing by twelve throws away which octave you played in and keeps only what you played. The result: inversions count, two-handed voicings count, doubling the root three times counts. The matcher never learns the difference, because there is no difference worth learning. 

std::array<bool, 12> pitchClassesForNotes (const std::array<bool, 128>& notes) const
{
    std::array<bool, 12> held {};

    for (auto note = 0; note < (int) notes.size(); ++note)
        if (notes[(size_t) note])
            held[(size_t) (note % 12)] = true;   // every C is a C

    return held;
}
Source/Main.cpp

Nothing missing, and not too much extra

A chord is stored as twelve booleans, so comparing is just counting three things: tones the chord needs that you are not holding, tones you are holding that the chord does not want, and the total. Every required note must be present — there is no partial credit. Extra notes are allowed only up to a budget that each chord carries with it, which is the subject of the next section. 

bool isChordMatch (const ChordSpec& chord, const std::array<bool, 12>& held)
{
    auto missing = 0, extras = 0, heldCount = 0;

    for (auto pc = 0; pc < 12; ++pc)
    {
        const auto required = chord.pitchClasses[(size_t) pc];
        const auto isHeld   = held[(size_t) pc];

        if (isHeld)               ++heldCount;
        if (required && ! isHeld) ++missing;
        if (! required && isHeld) ++extras;
    }

    return missing == 0
        && heldCount >= countPitchClasses (chord.pitchClasses)
        && extras <= chord.extraAllowance;
}
Source/Main.cpp

Right notes, wrong moment, still a miss

Correctness is only half of it — this is a rhythm game as much as a theory one. The check only runs while the hurdle's centre is inside a window 98 pixels either side of the runner — a little under two seconds at starting speed, and less as the lane speeds up. Hold the chord early and keep holding it and you will clear; stab at it late and the hurdle is already past you. 

const auto hurdleCenter = hurdle.x + hurdle.width * 0.5f;
const auto inClearZone  = std::abs (hurdleCenter - clearX) <= currentClearWindow();

if (! hurdle.judged && inClearZone && isChordMatch (chord, held))
{
    hurdle.judged  = true;
    hurdle.cleared = true;
    ++clearedHurdles;
    ++streak;
    score += 60 + countPitchClasses (chord.pitchClasses) * 15 + streak * 5;
}
Source/Main.cpp

Harder chords are worth more, on purpose

The score formula pays you for the number of distinct tones in the chord, so a five-note 6/9 is worth more than a three-note triad, plus a streak bonus that grows the longer you stay clean. If instead the hurdle runs off the left edge unjudged, the game hands off to rewindForChord() and the teaching pause takes over — no life lost, no points deducted, streak reset to zero. 

// The hurdle has passed the runner without being judged.
if (! hurdle.judged && hurdle.x + hurdle.width < clearX - 18.0f)
{
    rewindForChord (i);
    return;
}

05Engineering decisions

Six choices, and what each one bought.

Anyone can list a stack. These are the trade-offs I would defend in a review.

Musical correctness

Chords are compared as pitch classes, never as notes

Every chord is twelve booleans, and the comparison is a count, not a lookup. The alternative — storing chords as note numbers — would require enumerating every inversion, every octave and every two-handed spread of all 204 voicings, and it would still reject something a real pianist plays. Folding to twelve makes the whole class of "that was right and it said no" bugs impossible rather than merely rare.

Fairness

Every chord carries its own tolerance for wrong notes

Triads, sevenths, sus and diminished chords allow no extra notes at all; every extended, altered, rootless and quartal voicing allows exactly one. Without a budget you can clear any hurdle by holding down the entire keyboard, which technically contains every chord. Without some tolerance, a five-note 6/9 played with one added colour tone — which is how gospel players actually voice it — gets marked wrong. The allowance is a per-chord field, so tuning fairness never means touching the matcher.

Real-time audio

The game and the audio thread share state through atomics

Root, bass note and chord mask are std::atomic, written by the game and read inside the audio callback. The audio callback runs on a deadline measured in milliseconds; if it waits on anything, the speakers click. Publishing the harmony as three atomic values means the band picks up your chord change at the next step without the two threads ever blocking each other — and a transport reset is requested with a single exchange rather than a message queue.

Footprint

The backing band is generated, not recorded

Zero audio files ship with the game. Kick, snare, hi-hat, bass, pad and organ are all built from oscillators and noise at runtime. A sampled band means licensing every loop, shipping tens of megabytes, and being locked to whatever keys and tempos were recorded. A synthesised one follows your chord into any of the twelve keys for free, and the entire installer stays under four megabytes. The trade is honest: it sounds like a drum machine, not like a church.

Scope

One source file, and a clear point at which that stops being right

The entire application is 1,819 lines of Source/Main.cpp — synth, band, chord bank, game loop, rendering and UI. For a project this size that is a feature: no headers to keep in sync, no build graph, and the whole thing readable in one pass. It is also the first thing I would undo. The chord bank and the accompaniment engine are already independent of the game loop and want to be their own translation units the moment a second screen or a test suite exists — and the absence of tests is a direct consequence of never having split them out.

Trust

The installer never asks for administrator rights

It installs to %LOCALAPPDATA%\Programs, writes its uninstall entry under HKCU, and touches nothing machine-wide. A per-user install runs on a locked-down laptop, needs no password prompt, and can be completely removed by one uninstaller that deletes its own directory. Asking a musician for admin rights to try a practice game is a good way to have them not try it.

06The band

A full band, in about 300 lines, and no audio files at all.

This started as a complaint — playing chord after chord in silence was boring — and turned into the most interesting code in the project. The reference was the auto-accompaniment on a Yamaha arranger keyboard: you hold a chord, and a band plays that chord back at you in a style you picked.

// Four styles. Everything the band does is
// derived from this table plus six predicates.
static constexpr std::array<StyleDefinition, 4> styles {{
 // name           bpm  /beat /bar  drum  bass  pad  organ
  { "Slow 6/8",     72,  3,   12,  .58f, .34f, .20f, .14f },
  { "Worship Pad",  76,  4,   16,  .30f, .22f, .28f, .08f },
  { "Shout",       138,  4,   16,  .68f, .36f, .12f, .20f },

// Shout puts the kick on 1, the "and" of 1, 3 and the
// last sixteenth — the push that makes a shout feel urgent.
bool shouldTriggerKick (int style, int step) const
{
    if (style == 0) return step == 0 || step == 6;
    if (style == 1) return step == 0 || step == 10;
    if (style == 2) return step == 0 || step == 3 || step == 8 || step == 14;

    return step == 0 || step == 7 || step == 10;
}

The band follows your left hand, not the game

Sixty times a second the game takes whatever notes you are currently holding and asks which of the 204 chords in the bank they most resemble. This is a scoring problem rather than a lookup: matched tones add, missing and extra tones subtract, and holding the chord's root or putting it in the bass each earn a small bonus. That is how the band tracks you through a half-played voicing instead of dropping out until you get it exactly right.

The lowest note you are holding becomes the bass, independently of the chord name — so playing a C major triad over an A in the bass gets you a band playing C/A, exactly as an arranger keyboard would. If you are not holding anything, it falls back to the chord on the approaching hurdle, so the music never stops making sense.

Each part is then confined to its own register: the bass is folded down below MIDI note 49, the pad lives between 55 and 78, the organ between 60 and 82. That is the whole arrangement engine — no voice-leading model, just three windows that stop the parts from colliding. 

// Walk up from the root; put each chord tone into this part's register.
for (auto interval = 0; interval < 12 && count < (int) notes.size(); ++interval)
{
    const auto pc = root + interval;

    if (! maskContainsPitchClass (mask, pc))
        continue;

    auto note = midiNoteAtOrAbove (pc, lowNote);

    while (note > highNote) note -= 12;   // too high? drop an octave
    while (note < lowNote)  note += 12;   // too low? raise one

    if (note <= highNote)
        notes[(size_t) count++] = note;
}

if (count < 3)                                  // a rootless or quartal voicing left
{                                                 // the window nearly empty — fall back
    const auto fallback = maskFromIntervals (root, { 0, 4, 7 });   // to a plain triad
    // ...
}

07Shipping it

Getting it onto somebody else's laptop.

A game that only runs on the machine that compiled it is a hobby. The brief was one file you can email to a friend. Windows makes this harder than it sounds when none of the usual installer tools are on the machine.

  • 01

    CPack, then NSIS, then Inno, then WiX — none installed

    CMake can drive all of them and had none of them to drive. Installing a whole packaging toolchain to ship a four-megabyte game felt like the wrong direction.

  • 02

    IExpress is built into Windows, and it did not work

    Windows' own self-extractor got as far as writing its intermediate cabinet-file recipe and then failed silently with exit code 1. The recipe named an empty output directory, which makecab refuses. Two attempts to steer it from the config file changed nothing.

  • 03

    The answer was to stop looking for a tool and write one

    The setup file is now a 160-line C# program with the payload zip embedded as a resource, compiled by the .NET Framework compiler that ships with Windows. It extracts to a temp folder, runs the install script, and deletes the folder on the way out.

  • 04

    The runtime DLLs travel with it

    The release build links the MSVC runtime dynamically, so the packager copies the matching redistributable DLLs into the payload. Without that, the game fails to start on a clean laptop with an error naming a file nobody has heard of.

// Never trust a path that came out of a zip file.
var destinationRoot = Path.GetFullPath(destinationDir);
var destinationPath = Path.GetFullPath(
    Path.Combine(destinationDir, entry.FullName));

if (!destinationPath.StartsWith(destinationRoot,
        StringComparison.OrdinalIgnoreCase))
    throw new InvalidOperationException(
        "Installer payload contains an unsafe path.");
packaging/SetupBootstrapper.cs

A zip entry is allowed to be called ..\..\Windows\System32\something.dll. Extracting archives without checking where each entry lands is how the classic path-traversal bug gets shipped, so the bootstrapper resolves every destination to a full path and refuses anything that escapes the folder it was given — even though it only ever unpacks its own payload.

Verification

The installer has a quiet mode so it can be tested for real

Passing /quiet suppresses the finished dialog, which is what makes an automated install-then-uninstall test possible at all. The setup was then actually run: install, confirm the executable, both shortcuts, the uninstall script and the registry entry all exist, then run the uninstaller and confirm the directory and the registry key are gone. The first attempt at that test reported failure because PowerShell does not wait for a GUI-subsystem process — the checks ran before the installer had finished.

Clean removal

The uninstaller deletes the folder it is running from

A script cannot remove its own directory while Windows has it open, so it writes a tiny cleanup script to %TEMP%, launches it detached, and exits. The cleanup sleeps for a second, removes the install folder, then removes itself. It is a small trick, and it is the difference between a clean uninstall and leaving an empty folder plus a dead Start Menu entry behind on someone else's computer.

09Honest limitations

What it does not do yet.

Every one of these is a known trade-off rather than an oversight.

  • 01

    The original ambition — hearing chords in a recording — was cut

    This began as a question about detecting chords, inversions included, from a finished song. That is an open research problem, it needs a labelled dataset I do not have, and it would have been the entire project. Recognising chords from MIDI, where the notes are already known exactly, is a different and completely tractable problem — so the game plays MIDI.

  • 02

    The audio thread takes a lock

    The held-note table is guarded by a mutex, and note events are delivered while the audio callback is running. It has never audibly glitched, because the critical section is a single array write and nothing else contends for it — but taking any lock on an audio thread is a rule this breaks knowingly. A lock-free bitmask of two 64-bit atomics would remove the argument entirely.

  • 03

    It opens the first MIDI device it finds and never looks again

    No device picker, no hot-plug handling. Plug your keyboard in after launching and you have to restart the game. With one keyboard on the desk this is invisible; with two it is the first thing you would complain about.

  • 04

    There are no automated tests

    The chord matcher is pure, deterministic and about twenty lines — it is the easiest thing in the project to test, and it is untested, because the whole application is one file with no build target to link a test runner against. That is the concrete cost of the single-file decision, and it is why splitting the chord bank out is first on the list.

  • 05

    Windows only, and the installer is unsigned

    JUCE is cross-platform and the game code has nothing Windows-specific in it, but the packaging is entirely PowerShell and the .NET Framework compiler. Because the setup file is not code-signed, Windows SmartScreen warns the first person who runs it — which is exactly the moment you least want a scary dialog.

Where it goes next

Splitting the chord bank and the accompaniment engine into their own translation units, then putting the matcher under test — that unlocks everything else and costs an afternoon.

After that, the feature I actually want is a record of which chords you keep missing. The game already counts reviews; it throws away which chord each one was. Keeping that turns a practice game into a practice plan, and it is maybe thirty lines plus a settings file.

Longer term, the honest upgrade to the band is velocity and swing. Every hit currently lands dead on the grid at a fixed level, which is exactly why it reads as a drum machine. Neither is hard; both are the difference between something you tolerate and something you would practise to.

10How this was built

The brief fit in one sentence. Then it changed twice.

Gospel Chord Hurdles was built with an AI coding agent across four sessions between 30 June and 6 July 2026. I set the problem, made the product calls, and said when the thing I had been handed was the wrong thing; the agent wrote the implementation and ran the builds. Every quote below is verbatim from the session logs, which are linked at the end — typos included.

  1. 01Session 1 · 30 Jun

    design a game using C++ and juce that has hurdles only passed by playing gospel chords with increasing difficulty

    The entire specification, in one sentence. Genre, language, framework, win condition and progression, with nothing left over. "Only passed by playing" is the load-bearing phrase: it rules out a jump button, a skip, and any way through that does not involve your hands being right. The finished game does not do anything that is not in that line.

  2. 02Session 2 · 1 Jul

    do you think we can add like some tracks to play along to because right now it seems very boring to just play chord after chord with nothing in the background. what would that take?

    Boredom reported as a defect. The build was working exactly as specified and was no fun, which is a real bug in a practice tool: an app you do not open teaches you nothing. The proposals came back as a ladder — looping audio, then tempo-aware prompts, then stems, then a generated band — and the cheapest rungs were skipped because of what happened next.

  3. 03Session 2 · 1 Jul

    so you know how in some yamaha keyboards, they have this function where it plays a track and a full band with a progression that is dictated by notes you play, mostly in the bass. you know about that?

    Naming the reference replaced a design discussion. "Backing track" and "auto-accompaniment that follows your left hand" sound similar and are completely different builds — one is a file you play, the other is a band that listens. Pointing at a machine that has done this since the 1980s settled the architecture in one message: detect the chord, detect the bass note, drive a step sequencer from both. That is section 06.

  4. 04Session 1 · 1 Jul

    ok so this game is supposed to be more of learning than challenging/testing, so the cords should be in different sections, I shouldn't move from playing simple triads immediately into sus and 9ths. I should be able to select from a menu which voicings I would like to practice. If I fail a certain chord, the game should rewind a little bit, tell me the chord tones, ask me if I'm ready to continue and then continue on click. also the game shouldn't start immediately I launch the file, that's weird.

    The message that rewrote the product. Four separate corrections, each one invalidating something that was already built and working: the difficulty model, the chord ordering, the failure state and the launch behaviour. None of it was a bug. It was all delivered exactly as asked, and it was the wrong game — the sort of judgement no test suite makes for you. Everything in section 03 comes from these four sentences.

  5. 05Session 3 · 1 Jul

    the game looks really good so far. however, many of the buttons are poorly positioned, covering other important information on the screen. fix that. Also include a stop button that someone can just click to stop playing.

    A rendering-order bug, reported as a layout complaint. The real buttons are operating-system widgets living on top of a canvas the game paints every frame; both were using the same strip of screen, and the widgets always win. The fix was to reserve a real toolbar at the top, paint the heads-up display below it, and add a minimum window size so the two regions can never be squeezed back into each other.

  6. 06Session 4 · 6 Jul

    package/repackage the game so that I can install it onto another laptop using just a set up file

    One sentence, and by far the longest session. "Just a setup file" is a complete requirements document — one artefact, no prerequisites, no instructions — and meeting it took two dead ends and a setup program written from scratch. The follow-up questions were the right ones to ask and are answered in section 07: what exactly does the other laptop need, and what happens when Windows distrusts an unsigned file.

What I decided

  • The premise: hurdles cleared by playing an instrument, not by pressing a key
  • That it was a teaching tool rather than a test — and that this made the failure state, the difficulty ramp and the launch flow all wrong
  • That the player picks which voicings to drill, because triads before sus chords is not a matter of survival time
  • That silence was a defect, and that a Yamaha-style band was the specific fix
  • That the finished thing had to install on someone else's laptop from one file, with nothing else to install first

What the agent did

  • Wrote the JUCE application: chord bank, matcher, game loop, synth, rendering and UI
  • Turned the arranger-keyboard reference into a step sequencer with four styles and register-constrained voicings
  • Rebuilt the flow around PracticeState and the teaching pause when the brief changed
  • Diagnosed the stale CMake cache, the missing executable and the IExpress failure below
  • Built the installer and ran the install-then-uninstall verification on a real machine

11What broke

Five failures worth writing down.

None of these are in the source, so they are invisible to anyone reading the repository. They are most of where the time actually went.

Build system

Moving the project folder broke the build, and the error blamed the wrong thing

CMake writes the absolute path of its build directory into its cache, so after the project moved out of OneDrive every build failed with a complaint about a directory that no longer existed. The fix is not to edit the cache but to abandon it: rename the old build folder, configure fresh, and point JUCE_DIR at the JUCE checkout still sitting inside the old one so the framework did not have to be downloaded again.

Toolchain

"There's nothing in the Release folder" — and there wasn't

JUCE does not put the finished application where CMake normally would; it goes into a nested artefacts directory whose path nobody guesses on the first try. Rather than document where the file hides, the build was changed to put it somewhere obvious: a top-level dist/<config>/ folder set by RUNTIME_OUTPUT_DIRECTORY. Being unable to find the thing you just built is a real defect, and it is fixed in the build script, not in a README.

Packaging

IExpress failed with exit code 1 and no message

Windows' built-in packager produced its intermediate cabinet recipe and then stopped, silently. Reading that generated file showed an empty output directory, which makecab rejects; the documented option to embed the payload instead changed nothing, and the binary contained no useful strings. The decision that mattered was to stop debugging a legacy tool and spend the same time writing a 90-line replacement — which then worked first time and is far easier to reason about than the thing it replaced.

Environment

The agent could not find the project, twice

Two sessions opened with the tool searching the disk for its own workspace: the recorded project path still pointed into OneDrive while the real folder had moved to Documents. Both sessions burned real time on this before touching any code. It is the least glamorous entry here and probably the most useful — an agent's picture of your machine is just another cache, and it goes stale exactly like CMake's did.

Verification

The first installer test passed the wrong thing

The smoke test launched the setup file and immediately checked for installed files. They were not there — not because the install failed, but because Windows does not make the shell wait for a GUI process, so the assertions ran while the installer was still copying. A test that races the thing it is testing will report both false failures and false passes; re-running it with an explicit wait turned it into an actual verification.
